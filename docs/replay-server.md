# 通关录像服务（方案草案）

开发者要求：做一个服务器保存玩家的通关数据。玩家以较低战力通关某个关卡时，自动上传这一战的录像；卡在这一关的玩家可以下载别人的录像参考布阵。

本文是方案，**尚未实现**。下面的“默认”是先选定的做法，开发者确认或改动后再写代码。

---

## 1. 为什么能做：录像只需存“输入”

战斗内核是纯 C# 的确定性模拟（决策 21）：Q48.16 定点数、xorshift 随机数、固定每秒 20 帧，玩家操作通过 `BattleSim.Issue` 按帧注入。同样的输入一定得到同样的结果，所以录像不用存每一帧的画面或坐标，只存：

- 关卡 id 和随机种子
- 我方布阵（每名角色的位置、等级、星级、符文）
- 战斗中的指挥官技能指令（第几帧、哪个技能、落点）

一场 90 秒的战斗录像约 1~3 KB。观看时客户端用同样的输入重新跑一遍内核，3D 舞台照常表现。服务器也能用**同一份内核源码**重跑一遍来验证录像是真的（见第 5 节）。

---

## 2. 玩家看到什么

**上传（默认开启）**

- 通关后，如果这一战的战力低于该关卡“最低战力榜”的门槛（或榜单还没满），后台自动上传，不打断游戏。
- 结算界面角落提示一行“你的录像已进入本关最低战力榜第 3 名”。
- 设置里有“分享我的通关录像”开关；第一次上传前弹一次说明（会显示 Steam 昵称），玩家可以关掉。
- 游戏已改为必须联网登录（服务端设计见 server-design.md，PR #8）：战斗本来就在服务端结算重跑，结算后直接收进录像榜，不需要单独上传，也不需要本地上传队列。

**下载参考**

- 关卡详情页多一个“参考录像”按钮（同一关失败 2 次后在失败界面也提示一次）。
- 列表显示：战力、阵容缩略（几名角色和星级）、是否用了指挥官技能、Steam 昵称、点赞数。
- 点开后进入战斗界面观看，可暂停、倍速、拖动进度条（从快照重跑，见第 7 节）。
- “照抄布阵”：把录像里的布阵套到自己的布阵界面上，没有的角色留空、站位保留，玩家自己补。

## 3. 战力怎么算

“最低战力”是排名依据，必须**由内核根据布阵计算**，不能由客户端报一个数：

```
上阵战力 = Σ 每名上阵角色的战力
角色战力 = (生命 + 护盾) × 星级耐久倍率 × durability + 每秒伤害 × 星级伤害倍率 × dps   （取整）
```

- 已实现：`PowerRating`（`Runtime/Battle/Replay/PowerRating.cs`），权重在 `power.json`（目前 durability = 1、dps = 10，例如 ★1 重甲骑士 = 900 + 25 × 10 = 1150）。内核用定点数计算、取整。
- 等级和符文还没进内核（4.8 节是草案），加入后在同一个公式里补权重；录像里的布阵也要加对应字段，同时把 `format` 加 1。
- 威慑规则（5.4 节）本来就要比较双方战力，可以共用这一个公式。
- 魔网节点（源晶塔、法力水晶）算不算战力、指挥官技能用没用要不要区分，待定。**默认**：节点不算战力；用了技能的录像照常排名，但在列表上标出来，并提供“只看未用技能”筛选。

## 4. 录像格式

JSON，上传时 gzip。定点数一律存原始整数（`raw`），不经过小数，保证读回来逐位一致。

```json
{
  "format": 1,
  "kernel": 1,
  "data": "0801b7a62bed9a05",
  "stage": "patrol",
  "seed": "7739812231",
  "power": 1840,
  "player": [
    { "unit": "battleship", "depth": 0, "row": 3, "star": 2 },
    { "unit": "relay",      "depth": 2, "row": 4, "star": 1 }
  ],
  "commands": [
    { "tick": 412, "skill": "OrbitalStrike", "x": 5242880, "y": 196608 }
  ],
  "result": { "winner": 0, "ticks": 1386, "hash": "c0ffee0123456789" }
}
```

| 字段 | 说明 |
|---|---|
| `format` | 录像格式版本，格式变了 +1 |
| `kernel` | 内核规则版本（`Replay.KernelVersion`）；改了战斗规则就加 1 |
| `data` | 配置表内容的哈希（`GameData.Fingerprint`，按 `GameData.Files` 的顺序对所有 JSON 计算，先去掉 BOM 和 `\r`，Windows 和 Linux 结果一致）；改了数值就会变 |
| `seed` | 见下面“种子” |
| `power` | 客户端算的战力，服务器会重算并覆盖 |
| `commands` | 按帧排序的指挥官指令 |
| `result.hash` | 战斗结束时 `BattleSim.ComputeStateHash()` 的值，用来核对重跑结果 |

**种子（每关固定）**：关卡战斗的种子取 `StageSeed.For(关卡 id)`，不随每次挑战变化。客户端 `BattleController` 已改为：从配置表创建的关卡用固定种子，手工搭的测试战斗仍用时间种子。

- 如果客户端能自己选种子，作弊者可以反复换种子，挑出一个“运气好”的低战力胜局；固定种子堵住这个漏洞。
- 所有玩家面对的随机性一样，别人照抄布阵和技能时机就能打出同样的结果，录像的参考价值更高。
- 代价：同一关每次打的随机结果一样。暴击、闪避等随机因素影响不大，可以接受；如果想保留变化，改为“服务器每天发一个种子”也行，录像里照存。

## 5. 服务器：用内核重跑来防作弊

上传的录像不直接相信，服务器按下面顺序检查，任何一步不过就拒收：

1. **身份**：Steam 登录票据有效（第 6 节）。
2. **频率**：每个账号每关每天最多 N 次上传。
3. **格式**：字段齐全，布阵符合 `FormationRules`（格子、占位、上阵人数、指挥点上限），等级不超过星级上限。
4. **版本**：`kernel` 和 `data` 必须是服务器当前支持的版本。
5. **重跑**：用服务器上的配置表和关卡数据构造战斗，按录像注入指令跑到结束，检查我方获胜、帧数和 `hash` 一致。
6. **战力**：服务器自己算战力，写入记录。

能防住的：改胜负、改战力、改数值（服务器用自己的配置表，改过数值的客户端重跑结果对不上）、刷种子。

防不住也无所谓的：玩家改存档给自己加了没有的角色。录像本身仍是一套“真能打赢”的布阵，对参考没有坏处；而战力是按实际上阵属性算的，改高属性只会让战力变高、上不了榜。

重跑的成本：一场最多 1800 帧，内核在 .NET 上单场几毫秒，一台小服务器每秒能验证上百场，不是瓶颈。

---

## 6. 身份：用 Steam 账号，不做注册

- 游戏是 Steam 买断制，没有自己的账号系统。客户端通过 Steamworks 取一张 Web API 登录票据（`GetAuthTicketForWebApi`），服务器调用 Steam Web API `AuthenticateUserTicket` 换出 SteamID。
- 服务器只存 SteamID 和上传时的昵称；不收集邮箱等其他信息。
- 玩家可以在设置里删除自己上传的全部录像（GDPR 要求可删除）。
- 昵称不当可以被举报，管理员隐藏。

## 7. 架构与技术选型

```
Unity 客户端 ──HTTPS/JSON──▶ 录像服务（ASP.NET Core，.NET 8）──▶ PostgreSQL
                                   │
                                   └─ 引用 Starline.Battle（与客户端同一份内核源码）
```

| 选择 | 理由 |
|---|---|
| ASP.NET Core 最小 API | 和内核同语言，直接引用 `src/Starline.Battle` 编译的同一份源码，验证逻辑零重写 |
| PostgreSQL | 录像只有几 KB，直接存在表里（`jsonb` 或 `bytea`），不需要单独的文件存储；量大了再挪到对象存储 |
| 单台云服务器 + Docker | 个人开发者运维成本最低；前面加 CDN 缓存“下载录像”这种只读请求 |
| 不用游戏服务器框架、不做长连接 | 只有上传和查询两类请求，普通 HTTP 足够 |

**接口**

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/auth/steam` | 用 Steam 票据换一个短期访问令牌 |
| GET | `/v1/stages/{stage}/board?data={hash}` | 本关最低战力榜（前 20 名的摘要和上榜门槛） |
| GET | `/v1/replays/{id}` | 下载一份录像 |
| POST | `/v1/replays/{id}/like` | 点赞 |
| POST | `/v1/replays/{id}/report` | 举报 |
| DELETE | `/v1/me/replays` | 删除我上传的全部录像 |

**数据表（主要两张）**

- `replays`：id、stage、data 版本、kernel 版本、steam_id、昵称、战力、用没用技能、阵容摘要、录像内容、点赞数、状态（正常 / 隐藏 / 旧版本）、上传时间。
- `players`：steam_id、昵称、是否封禁、上传计数。

**榜单规则（默认）**：每关、每个数据版本保留战力最低的 20 份；同一玩家在同一关只保留自己最好的一份；同战力按上传时间先后排。

## 8. 版本更新时的录像

调整数值后（`data` 哈希变了），老录像在新版本里重跑结果可能不同。

- 发布新版本时，服务器把每关榜上的老录像用新数据批量重跑一遍：仍能赢的迁移到新版本（战力重算），打不赢的标记“旧版本”，不再出现在新版本的榜单里。
- 客户端只请求和自己 `data` 哈希一致的榜单，不会看到对不上的录像。
- 服务器同时保留最近两三个版本的配置表，兼容没更新的玩家。

## 9. 确定性的风险和要补的测试

内核只用整数运算，.NET（服务器）和 Unity（Mono / IL2CPP）上结果应当一致，但要用测试兜底：

- 测试项目里的“黄金录像”（`tests/Starline.Battle.Tests/ReplayTests.cs`）：配置表没变而战斗结果变了就报错，提醒把 `Replay.KernelVersion` 加 1；配置表改了则打印新的哈希，照着更新测试里的三个常量即可。
- Unity 里加一个编辑器菜单，跑同一批黄金录像，确认和 .NET 结果一致（IL2CPP 打包后也跑一次）。
- 继续遵守约定：不用 float、不用 `System.Random`、不依赖字典遍历顺序。

## 12. 多平台：团结引擎 + UOS

开发者考虑以后同时发布微信小游戏、Steam、安卓、iOS，并问团结引擎和它的云服务（UOS）能不能让服务器和多渠道分发简单一些。开发者已选定“团结引擎 + 混合后端”（决策 42）。

**引擎**：Unity 6 已不向中国用户提供，团结引擎基于 Unity 2022 LTS 定制，可以全球发行（含 Steam），年收入低于 20 万美元免费。它最大的好处是有现成的微信小游戏转换流程；Steam、安卓、iOS 的构建 Unity 本来就支持。战斗内核是纯 C#，不受影响；客户端需要新建团结工程，把 `com.starline.game` 包搬过去，重点检查 URP 版本、UI Toolkit 和自动配置 URP 的编辑器脚本。

**后端分工（全部托管到 UOS）**

开发者先选了“混合后端”，随后要求服务端全部托管到 UOS 试一下。UOS 的云函数支持 C#，所以录像校验也能放上去，不用自己维护服务器。

| 职责 | UOS 服务 | 说明 |
|---|---|---|
| 小游戏资源分包、CDN | CDN | 0.15 元/GB |
| 录像上传、重跑校验、最低战力榜接口 | Func Stateless（C# 云函数，HTTP 触发） | 每次校验只跑几毫秒，按 GB·秒计费（0.0001 元/GBs，另加 0.12 元/万次调用），最大 100 QPS |
| 录像和榜单数据 | CRUD Save / Storage | 录像只有几 KB，存储费用很低 |
| 账号 | Passport：微信小游戏登录；Steam、iOS 走“外部 ID 登录”，由云函数先校验 Steam 票据再映射 | 计费页写的是“0.06 元 × DAU/天”，按字面理解 1000 日活每月约 1800 元，是最大一笔开销，需要找 UOS 确认口径 |
| 云存档、远程配置 | Cloud Save、Remote Config | 远程配置按次计费，很便宜 |

**数据库**：放在 UOS 托管，不自己维护。

- 先用 CRUD Save（按用量计费，起步每月几块钱）存录像、每关榜单、玩家。如果它不支持“按关卡筛选、按战力排序取前 20”，就由云函数维护一份排好序的榜单文档。
- 玩家多了、要做天梯和排行榜的复杂查询时，升级到 CRUD Storage（托管 MySQL，1 核约 3.20 元/天）。
- 客户端不直接连数据库，所有读写都经过云函数校验。
- 定期导出备份（录像本身是 JSON），防误删，也方便以后迁出 UOS。

**要先验证的三件事**（需要在 UOS 后台实际部署一次）

1. C# 云函数能否带上内核源码（`Starline.Battle` 作为共享代码或 NuGet 包），并且能读到配置表 JSON。
2. 云函数在国内能否稳定访问 Steam Web API（校验 Steam 票据要用）。
3. Passport 的计费口径。如果太贵，可以不用 Passport，改由云函数自己处理微信 `code2session` 和 Steam 票据，账号存在 CRUD 里。

**退路**：服务端代码分两层。校验逻辑写成普通 .NET 类库（`Starline.Replay`：读录像、重跑、算战力），UOS 云函数只是外面一层很薄的入口。如果第 1 条走不通，同一个类库可以打成 ASP.NET 程序部署到 Func Stateful（UOS 托管的 Docker 服务器，0.05~0.80 元/台·小时），或者部署到第 7 节的自建服务器，游戏和内核代码都不用改。

注意：UOS 部署在国内，海外 Steam 玩家上传、下载录像会慢一些，但这类请求对延迟不敏感，影响不大。UOS 的试用额度不能用于正式商用。

**客户端在线服务接口**：游戏代码只调用一个接口（登录、上传录像、拉榜单、云存档），每个平台写一个适配（Steam、微信、iOS、安卓）。换服务商或加渠道时只改适配，不动游戏和内核代码。

**还要注意**

- 各商店的上架流程（Steam 后台、App Store 审核、国内安卓商店）仍要各走一遍；国内手机端和小游戏要收费需要版号。
- UOS 的服务器在国内，海外 Steam 玩家访问可能较慢；录像服务部署在香港（第 10 节）可以兼顾两边。
- 商业模式会分叉：Steam 买断制，小游戏和手机端通常免费加广告或内购，数值和成长节奏要分开设计（决策 5 当时的顾虑）。
- 小游戏版的技术风险：首包体积（中文字体约 10 MB）、3D 战斗在 WebGL 上的性能、按 4K 设计的界面要缩小。
