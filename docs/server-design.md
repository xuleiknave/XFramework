# 服务端设计：联网以服务器为准，离线补交

开发者选定（决策 48）：**联网时养成数据以服务端为准，断网时照常玩，联网后把离线期间做的事按顺序补交，服务端逐个验证后再算数。** 本文是服务端的整体设计：怎么结算、离线怎么补交、工程怎么分、有哪些接口。表结构见 [server-database.md](server-database.md)，通关录像的规则见 [replay-server.md](replay-server.md)。

这一步仍是设计，还没有服务端代码。

---

## 1. 核心思路：提交“动作”，不提交“存档”

客户端不上传“我现在有多少金币、角色几星”，而是上传**它做了什么**：

| 动作 | 例子 |
|---|---|
| 打一场战斗 | 打 ch1-03：布阵 + 带帧号的指挥官指令 |
| 扫荡 | 扫荡 ch1-03 五次 |
| 养成 | 加文升到 ★3；把符文装到槽 2；碎片召唤灰爪 |
| 消费 | 在商店用金币买 10 个玛塔的碎片 |
| 计时 | 炼金工坊开始解析食尸鬼；领取 60% 成果 |
| 标记 | 读完第一章开场剧情；完成布阵教学 |

服务端收到动作后，用**和客户端同一份规则代码、同一份配置表**算一遍，结果写进数据库。这样：

- **在线和离线走同一条路**：在线时一次交一个动作，离线时攒一串，联网后一起交。服务端只有一套处理逻辑。
- **改存档没用**：客户端说“我有 999 个碎片”不算数，服务端只认自己算出来的。
- **两台电脑不会互相覆盖**：动作是“在当前状态上做一件事”，而不是“用我的存档覆盖你的”。A 电脑离线打了几关，B 电脑在线升了星，A 联网后它的动作接在 B 的结果后面继续执行。

### 前提：所有随机数都从存档状态推出来

离线时客户端先自己算结果（掉落、远征地图），联网后服务端要算出**一模一样**的结果，否则玩家会看到奖励“变了”。所以：

- 关卡掉落的种子 = `hash(存档 id, 关卡 id, 本关第几次通关)`
- 扫荡第 n 次的种子 = `hash(存档 id, 关卡 id, 本关通关 + 扫荡次数)`
- 远征的种子 = `hash(存档 id, 第几次远征)`
- 战斗本身的种子 = `hash(关卡 id)`（每关固定，replay-server.md 第 4 节）

这些计数都在存档里（`save_stage.clear_count`、`save_slot.runs_started`），客户端和服务端用同一个确定性随机数（xorshift）算，不会对不上。玩家也没法靠“读档重来”刷掉落，因为计数只增不减。

## 2. 规则代码放在内核里，客户端和服务端共用

现在内核（`Runtime/Battle`）只管战斗和远征。服务端要能算“通关给多少经验、升星花多少碎片、掉什么”，这些规则必须和客户端离线时算的完全一致，所以**养成规则也放进内核**，新加一个模块：

```
Runtime/Battle/Progression/      命名空间 Starline.Progression（纯 C#，不依赖 Unity）
  SaveState         存档在内存里的样子：货币、角色、符文、关卡、图鉴、高塔、工坊……
  Actions/          每种动作一个类：校验 + 执行，返回变化（Delta）
  Rewards           掉落表、经验、碎片
  PowerFormula      战力公式（录像榜也用）
```

- 规则：`Apply(SaveState 当前状态, 动作, 配置表, 时间) → 新状态 + 变化 / 拒绝原因`。纯函数，没有 IO。
- 客户端离线时直接调它，联网时也先本地调一遍（界面立刻有反应），再交给服务端确认。
- 服务端：从 MySQL 读出 `SaveState` → 调同一个 `Apply` → 把变化写回 MySQL。
- 数值都在 JSON 配置表里（项目约定），新增 `progression.json`（经验曲线、升星消耗、等级上限）、`stages.json`（主线关卡、掉落）、`shop.json` 等。
- 和战斗内核一样守确定性：不用 float、不用 `System.Random`、不依赖字典遍历顺序。测试项目里加“同一串动作在两个 SaveState 上执行结果一致”的测试。

## 3. 动作怎么交、怎么处理

### 3.1 客户端这边

- 每台电脑首次启动生成一个 `device_id`（UUID），存在本地。
- 每个动作带 `(device_id, client_seq)`，`client_seq` 在同一设备、同一存档内从 1 递增。
- 动作先存进本地队列（和存档同一个文件，先写临时文件再替换），再发送。服务端确认后从队列里删掉。
- 战斗动作附带战斗输入（录像格式）和客户端算出的结果哈希。

### 3.2 服务端这边

`POST /v1/saves/{id}/actions`，一次最多 200 个动作，必须按 `client_seq` 连续：

```
开事务，SELECT … FOR UPDATE 锁住这个存档（save_slot 那一行）
读出 SaveState
对每个动作：
  (save, device, seq) 已经处理过 → 直接返回上次的结果（网络重试不会重复发奖励）
  是战斗 → 用动作记录的 data_hash 对应的配置表和内核重跑（第 4 节），写 save_battle
  调 Progression.Apply
    通过 → 记下变化，revision + 1
    拒绝 → 记下原因，状态不变，继续下一个
  写 save_action
把所有变化写回各表，写 economy_log
提交事务
返回：每个动作的结果、新的 revision；有动作被拒绝时附带完整存档快照
```

- 一个存档同一时间只有一个请求在改（行锁），两台电脑同时交也不会乱。
- 动作之间有依赖时（先升星再装槽 3 的符文），前一个被拒、后一个也会因为条件不满足被拒，不需要特别处理。
- 处理完一批，客户端拿到的就是服务端的权威结果：
  - 全部通过：客户端本地早就是这个结果了，不用变。
  - 有被拒的：客户端用返回的完整快照**覆盖**本地存档，并提示“有 N 条离线记录没有通过验证”。

### 3.3 拒绝原因

| 代码 | 什么时候 | 玩家看到 |
|---|---|---|
| `battle_mismatch` | 重跑结果和客户端说的不一样（通常是改了数值或内存） | 这场战斗按服务端重跑的结果算：重跑也赢了就照常发奖励，输了就不发 |
| `invalid_formation` | 布阵不合法：没有的角色、超出指挥点、等级超过上限 | 这场战斗不算 |
| `not_enough_*` | 碎片、金币、遗骸不够 | 这一步没执行 |
| `locked` | 关卡、槽位、功能还没解锁 | 这一步没执行 |
| `version_unsupported` | 动作用的配置表版本服务端已经不支持（见 3.4） | 这场战斗不算，提示更新游戏 |
| `seq_gap` | `client_seq` 不连续 | 整批退回，客户端重发 |

被拒的动作都留在 `save_action`（`status = 2`）。同一账号短时间内大量 `battle_mismatch` 说明可能在作弊，进后台人工看，**不自动封号**（也可能是客户端的 bug）。

### 3.4 离线太久、游戏更新了

- 每场战斗都记着当时的 `data_hash` 和内核版本。服务端保留最近 90 天内发布过的配置表版本（`game_data_version`），用打这场时的版本重跑。
- 更老的版本（90 天以上没联网又没更新游戏）：战斗动作以 `version_unsupported` 拒绝，其余动作照常处理。
- 内核版本不能同时装好几份，所以**改战斗规则的版本**（内核版本变了）发布时，客户端联网先把队列交完再更新；交不上的老战斗也按 `version_unsupported` 处理。只改数值（配置表）不受影响。

### 3.5 计时类动作（炼金工坊）

离线时客户端用自己的时钟。服务端处理时把 `client_time` 夹到合理范围：不早于这个存档上一次被服务端确认的时间，不晚于服务端当前时间。研究完成与否以服务端时间判断，把本机时间调快只会让领取的动作被拒（还没完成），研究本身不受影响，下次再领即可。

### 3.6 不走动作的东西

- **游戏时长**：每次同步时客户端报一下增加的秒数，服务端只做上限检查（不超过两次同步之间的真实时间）。只用于展示，不影响养成。
- **设置**：`PUT /v1/me/settings` 带 `revision`，以最后一次写为准。
- **建档、改名、删档**：单独的接口（第 6 节），不进动作队列。离线时新建的存档联网后先建档再交动作。

## 4. 战斗验证

和 replay-server.md 第 5 节相同：服务端用同一份内核源码构造战斗，按记录的种子和指令跑到结束，比较胜负、帧数和状态哈希。

- 服务端用**自己存的**存档数据构造我方阵容（角色的等级、星级、符文），不信任客户端提交的属性。客户端只交“谁站在哪、什么时候放什么技能”。
- 一场最多 1800 帧，单场几毫秒。离线一周攒下几百场，补交也就一两秒。
- 重跑通过的战斗进 `save_battle`。玩家打出本关低战力胜局时，录像直接从这里取（第 7 节），不用再上传一遍。

## 5. 服务端工程结构

```
server/
  Starline.Server.sln
  src/
    Starline.Server.Api/       ASP.NET Core（.NET 8）最小 API：路由、登录鉴权、限流、序列化
    Starline.Server.Game/      动作处理：读 SaveState → 调内核规则 → 写回；录像榜；配置表多版本管理
    Starline.Server.Data/      MySQL 访问：MySqlConnector + Dapper，每张表一个仓储类
  tests/
    Starline.Server.Tests/     动作处理、离线补交、并发、重试幂等的测试（用 Docker 起 MySQL）
  db/
    schema.sql                 第一版表结构
    migrations/                之后的改动：0002_xxx.sql、0003_xxx.sql……启动时按序号执行（DbUp）
  deploy/
    Dockerfile、docker-compose.yml
```

| 选择 | 理由 |
|---|---|
| ASP.NET Core 最小 API | 和内核同语言，直接引用 `src/Starline.Battle`（再加上新的 Progression 模块），规则零重写 |
| Dapper 而不是 EF Core | 表结构是手写 SQL 定的，查询也简单；Dapper 轻、SQL 看得见，行锁和批量写更好控制 |
| MySqlConnector | 异步、性能好，MIT 协议 |
| DbUp 按序号执行 SQL | 迁移就是普通 SQL 文件，和 `schema.sql` 一个风格 |
| 配置表多版本 | 服务端启动时加载 `data/<data_hash>/` 下的每一版 StarlineData，按动作里的 `data_hash` 选 |
| 不加 Redis | 个人项目先少一个组件。限流用内存（单实例），会话在 MySQL；以后多实例再加 |

## 6. 接口

全部 HTTPS + JSON，路径以 `/v1` 开头。除了登录，都要带 `Authorization: Bearer <访问令牌>` 和 `X-Device-Id`。

### 登录与账号

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/auth/steam` | Steam 票据换访问令牌（15 分钟）和刷新令牌（30 天）；第一次登录自动建账号 |
| POST | `/v1/auth/refresh` | 用刷新令牌换新的一对令牌（旧的刷新令牌作废） |
| POST | `/v1/auth/logout` | 作废当前刷新令牌 |
| GET | `/v1/me` | 账号信息、已购内容、设置、存档列表（各存档的摘要和 revision） |
| PUT | `/v1/me/settings` | 改设置（带 revision） |
| GET / DELETE | `/v1/me/sessions[/{id}]` | 查看登录过的设备、踢下线 |
| DELETE | `/v1/me` | 注销账号：标记注销，30 天后真正删除 |

### 存档

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/saves` | 新建存档（存档位、指挥官名字） |
| GET | `/v1/saves/{id}` | 完整存档快照 + revision（换电脑、被拒后覆盖用） |
| PATCH | `/v1/saves/{id}` | 改指挥官名字 |
| DELETE | `/v1/saves/{id}` | 删除存档（软删除） |
| POST | `/v1/saves/{id}/actions` | 提交动作（第 3 节），在线和离线都用它 |
| POST | `/v1/saves/{id}/playtime` | 报告游戏时长 |

### 通关录像

在 replay-server.md 第 7 节的基础上，上传改成“分享一场已经验证过的战斗”：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/v1/stages/{stage}/board?data={hash}&noskill=0` | 本关最低战力榜 |
| GET | `/v1/replays/{public_id}` | 下载录像 |
| POST | `/v1/replays/{public_id}/like` | 点赞 |
| POST | `/v1/replays/{public_id}/report` | 举报 |
| DELETE | `/v1/me/replays` | 删除我上传的全部录像 |

不需要单独的上传接口：战斗动作被服务端验证通过后，如果玩家开着“分享我的通关录像”，而且这场战力能进榜，服务端**自动**把它收进录像榜，结果放在这个动作的返回里（“你的录像已进入本关最低战力榜第 3 名”）。离线打的关补交时也一样。

### 通用约定

- 错误统一返回 `{ "code": "not_enough_shards", "message": "碎片不够" }`，`code` 给程序判断，`message` 是中文，可以直接显示。
- 客户端版本太老（内核版本服务端已不支持）时，所有接口返回 `426`，客户端提示更新。
- 限流：每个账号每分钟 120 次请求；录像榜接口可以被 CDN 缓存 1 分钟。

## 7. 断网时玩家看到什么

- 主菜单右上角显示同步状态：已同步 / 有 N 条记录待同步 / 离线。
- 离线时所有玩法照常，只有在线功能（参考录像、排行榜）显示“需要联网”。
- 联网后自动在后台补交，不打断游戏。补交期间可以继续玩，新动作排在队尾。
- 有记录没通过时弹一次提示，列出哪几条、为什么（比如“第 1-3 关的战斗结果和服务器不一致，这场不计奖励”），然后存档变成服务端的版本。
- 从没联网过的玩家（纯单机）不受任何影响：本地存档照旧，第一次登录时把本地存档当作“新建存档 + 一串动作”交上去。为此本地要保留从建档开始的完整动作记录；记录太长时（比如超过 5000 条）退而求其次，按“导入本地存档”处理：服务端只做合理性检查（等级、星级、碎片不超过按通关进度能拿到的上限）后接受。

## 8. 要改的地方（按顺序）

| 阶段 | 内容 | 需要服务器 |
|---|---|---|
| S1 内核 | `Starline.Progression`：SaveState、动作、奖励、战力公式；配置表 `progression.json`、`stages.json`；确定性测试 | 不需要 |
| S2 客户端 | 本地存档改成 SaveState + 动作队列；所有养成操作都改为生成动作再调 `Apply` | 不需要 |
| S3 服务端骨架 | `server/` 工程、Steam 登录、存档接口、动作接口、配置表多版本、Docker 部署 | 需要 |
| S4 联网 | 客户端接 Steamworks 登录、后台同步、同步状态显示、被拒提示 | 需要 |
| S5 录像 | 录像榜、下载、点赞举报（replay-server.md 的 R2~R4） | 需要 |

S1、S2 不需要服务器，单机版也能直接受益（存档结构更清楚、动作队列顺便能做“撤销最近一次操作”之类的功能），可以先做。

## 9. 还没定的事

1. **从没联网过的老存档导入时，检查做多严**（第 7 节最后一条）。默认：有完整动作记录就逐条验证，没有就只做上限检查。
2. **离线战斗的配置表版本保留多久**。默认 90 天。
3. **部署地点**：沿用 replay-server.md 的默认（香港，不用备案），等你确认云服务器在哪。
